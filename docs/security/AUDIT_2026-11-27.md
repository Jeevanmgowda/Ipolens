## 1. Architecture and trust boundaries

### 1.1 Components
```
Browser (React client components, AuthContext keeps the user profile in localStorage)
   │  cookies: ipolens_session / ipolens_token (HttpOnly, SameSite=Lax, Secure in prod)
   ▼
src/proxy.ts  ── CORS allowlist + Origin check, in-memory per-IP rate limit (XFF-trusted),
   │             /admin cookie-presence check, /api/scraper/sync cookie-or-CRON pre-check
   ▼
Route handlers (src/app/api/**, 44 files)
   ├─ session.ts: opaque random token → in-memory Map + Postgres sessions table
   ├─ authStore.ts: in-memory user array (3 seeded demo users) + fire-and-forget DB insert
   ├─ DbRepositoryService: Drizzle/Postgres when DATABASE_URL set and circuit closed,
   │     else module-global in-memory arrays/maps (some NOT keyed by user)
   ├─ Redis (ioredis) or in-memory emitter fallback (cache, pub/sub "market-ticks")
   ├─ Gemini (@google/genai) ← user-supplied DRHP text / summaries / uploads
   ├─ Upstox REST (server token from env / .env.local), Angel One SmartAPI (worker)
   ├─ NSE / BSE / InvestorGain fetchers (fixed hosts)
   ├─ Registrar adapters (fixed hosts; live lookups gated → "unavailable")
   └─ child_process.exec → python scripts/scraper/merge.py (admin / CRON only)
Scripts (local only): getUpstoxToken.mjs (Puppeteer + mobile/PIN/TOTP, writes .env.local,
   opens a callback HTTP server), devWithUpstox.mjs (spawns next dev)
Worker: workers/market-feed-worker.ts (smartapi-javascript)
```

### 1.2 Trust boundaries and untrusted inputs
1. **Browser → API.** Request bodies, queries, path params, uploads (CSV, PDF and text), cookies and headers (`X-Forwarded-For`, `Origin`, `Authorization`) are all untrusted. **The client-side `AuthContext` login state isn't a security boundary.** `loginWithDemo` sets a localStorage user with no server session at all (`src/context/AuthContext.tsx:136-139`).
2. **API → Gemini.** Text the user supplies goes into prompts, so it can carry prompt injection. Model output is shown to users as investment verdicts.
3. **API ← third parties.** Responses from Upstox (including `user_name`), NSE/BSE/InvestorGain HTML and JSON, and registrar portals are untrusted data. Upstox output is reflected into HTML (H1).
4. **Server → filesystem and processes.** The Upstox callback writes `.env.local`. The scraper route runs Python and reads `data/ipos.json`.
5. **Local developer machine.** The scripts hold broker mobile, PIN and TOTP seed, and open a listening socket (M10).

### 1.4 Operations that must be enforced server-side
These must never be left to the client:
1. **Identity.** The ID-token signature, `aud`, `iss`, `exp`, `email_verified` and nonce must all be checked on the server. Accounts are found by verified email only.
2. **Ownership.** Every read or write of PANs, applications, holdings, notifications, watchlist, erasure and allotment must be scoped to `session.userId`. There must be no anonymous fallback bucket, and no in-memory fallback that ignores `userId`.
3. **Derived fields.** Holder name, PAN and relationship on an application must come from the caller's own PAN profile, not the request body. Role is decided on the server, not taken from the client's `investorCategory`.
4. **Numeric limits.** Lots, shares, bid price, blocked amount and allotted shares must be positive integers with upper bounds, and statuses an enum.
5. **SEBI one-PAN-one-bid duplicate check.** It must run on the server against the hashed real PAN, not masked strings.
6. **Admin actions.** These are the scraper run, Upstox OAuth and the token/status routes.
7. **AI.** Auth, per-user quota, input length caps, delimiting of untrusted text and output schema validation.
8. **Resource limits.** Body size, upload size and decompression caps, regex input length, SSE symbol and connection caps, and per-account login throttling.
9. **PAN cryptography.** A mandatory dedicated key, with masking and hashing done on the server.

### C1: Google sign-in accepts any email, so any account can be taken over
- **Vulnerability:** OAuth/SSO authentication bypass. Broken authentication, leading to privilege escalation.
- **Severity:** Critical.
- **Affected files:**
  - `src/app/api/auth/google/route.ts`
  - `src/services/authStore.ts`
- **Exact lines:**
  - `route.ts:9-10`
  - `authStore.ts:158-174`
- **Description:**
  - The route passes the raw JSON body to `registerOrLoginWithGoogle`, which looks the user up by `email` and returns that account.
  - The client sends `credential` (`GoogleAuthModal.tsx:126`), but the server ignores it and never verifies the Google ID token.
  - The client only decodes it, with `parseGoogleJwt` using `atob`, which is not a signature check.
- **Evidence:**
  - `const body = await request.json(); const result = registerOrLoginWithGoogle(body);`
  - `if (existingUser) { … return { valid: true, user: safeUser }; }`
  - No `jose`, `google-auth-library` or `verifyIdToken` appears anywhere (grep below).
- **Impact:**
  - `POST /api/auth/google {"email":"admin@ipolens.in"}` returns a valid 30-day session for the seeded **admin**. That unlocks the admin-only `POST /api/scraper/sync` (Python execution).
  - The same works for any registered user, giving full account takeover and access to their PANs, applications and holdings. It also lets anyone register accounts under any email.
- **Recommended fix:**
  - Verify the ID token on the server. Use `jose` `createRemoteJWKSet` with `https://www.googleapis.com/oauth2/v3/certs`, and check:
    - `aud = NEXT_PUBLIC_GOOGLE_CLIENT_ID`;
    - `iss ∈ {accounts.google.com, https://accounts.google.com}`;
    - `exp`;
    - `email_verified`;
    - a one-time nonce from an HttpOnly cookie.
  - Take `email`, `name` and `picture` only from verified claims. Reject the "local fallback" demo picker in production.
  - Candidate: `e0f8c5c` (verify Google ID tokens) plus `80abe41` (nonce) on the backup branch.
- **Implementation status:** Fixed (R1). Ported from `e0f8c5c`: `src/lib/security/googleIdToken.ts` verifies RS256 against Google's JWKS plus `aud`, `iss`, `exp` and `email_verified`; identity comes only from verified claims; the credential-less path is refused in production. The nonce (L4 in the old audit) is still open and belongs to R17.
- **Test result:** Regression tests in `tests/authHardening.test.ts` pass after the fix; the route tests fail on `ebd30a0`.

### C2: Anonymous callers can read every user's family PAN profiles
- **Vulnerability:** Broken access control / IDOR / BOLA (cross-tenant data exposure).
- **Severity:** Critical.
- **Affected files:**
  - `src/app/api/pans/optimize-allocation/route.ts`
  - `src/app/api/allotment/multi-scan/route.ts`
  - `src/lib/services/db-repository.service.ts`
  - `src/lib/services/registrar-scanner.service.ts`
- **Exact lines:**
  - `optimize-allocation/route.ts:13, 34-39`
  - `multi-scan/route.ts:8, 21-26, 42`
  - `db-repository.service.ts:98-105`
  - `registrar-scanner.service.ts:283-289, 334`
- **Description:**
  - Neither route checks for a session.
  - When the body has no `pans`, both use `getUserPansStore()`, a module-global array. `savePan` pushes **every** user's profile into it, even in database mode ("Always keep memory store synchronized").
  - Both routes also accept a client-supplied `pans` array.
- **Evidence:**
  - `profiles = getUserPansStore();` in both routes.
  - The optimizer copies `holderName: p.name, panMasked: p.pan` into the response (`allocation-optimizer.service.ts:176-178`).
  - `multi-scan` passes `autoSyncDatabase: Boolean(autoSyncDatabase)` (default `true`) into `updateApplicationStatus(app.id, …)`.
- **Impact:**
  - Any internet user can list every customer's family member names, relationships and masked PANs.
  - `multi-scan` can also rewrite the status and allotted shares of other users' applications in memory.
- **Recommended fix:**
  - Require a session.
  - Load only `DbRepositoryService.getPans(user.id)`.
  - Ignore client `pans`.
  - Remove `multi-scan`, or make it user-scoped.
  - Stop mirroring all users into one global array.
  - Candidate: `aec8875`.
- **Implementation status:** Fixed (R2). `optimize-allocation` requires a session and loads `getPans(user.id)`; client-sent profiles only narrow the selection by ID; `allotment/multi-scan` is deleted; the scanner service now requires a `userId`.
- **Test result:** Regression tests in `tests/securityRemediation.test.ts` (R2 suite) pass after the fix and fail on `ebd30a0`.

### C3: Personal-data routes fall back to a shared anonymous bucket, and the in-memory fallback ignores `userId`
- **Vulnerability:** Broken access control / IDOR, RLS-equivalent bypass and session-management failure.
- **Severity:** Critical.
- **Affected files:**
  - `src/app/api/pans/route.ts`
  - `src/app/api/applications/route.ts`
  - `src/app/api/notifications/route.ts`
  - `src/app/api/market/watchlist/route.ts`
  - `src/app/api/portfolio/holdings/route.ts`
  - `src/app/api/portfolio/upload/route.ts`
  - `src/app/api/user/data/route.ts`
  - `src/lib/services/db-repository.service.ts`
- **Exact lines:**
  - `pans/route.ts:17, 31, 87`
  - `applications/route.ts:31, 50`
  - `notifications/route.ts:9, 23`
  - `watchlist/route.ts:9, 24`
  - `holdings/route.ts:9, 55`
  - `upload/route.ts:9`
  - `user/data/route.ts:12`
  - `db-repository.service.ts:62, 125-130, 177-181`
- **Description:**
  - **The anonymous bucket.** Every handler does `const userId = user ? user.id : 'default_user';`. All anonymous visitors, and every user of the client-only "demo login" (which creates no server session), share one data bucket. Anyone can read, add or purge it (`DELETE /api/user/data`).
  - **The in-memory fallback.** When there's no `DATABASE_URL`, when the DB circuit breaker is open (60 s after any network error, see `src/db/index.ts:63-66`), or when a query throws:
    - `getPans` returns `getUserPansStore()`, i.e. **all** users' PANs;
    - `getApplications` returns `getApplicationsStore()`, i.e. **all** users' applications;
    - in both cases `userId` is ignored.
  - In-memory `deletePan` removes by `id` regardless of owner.
- **Evidence:**
  - `return getUserPansStore();` (`:62`)
  - `let list = getApplicationsStore(); if (symbol) { … } return list;` (`:177-181`)
- **Impact:**
  - Any visitor can read other people's family PAN profiles and applications whenever the DB is unavailable, which also happens deliberately if an attacker can trigger DB timeouts.
  - Anonymous users and demo users always share and overwrite each other's data.
  - DPDP erasure deletes the shared bucket rather than the user's own data.
- **Recommended fix:**
  - Add a `requireUser()` helper that returns 401 when there's no session. Remove every `'default_user'` default parameter.
  - Key every in-memory fallback by `userId`, or refuse to serve personal data when the DB is down.
  - Remove client-only `loginWithDemo`.
  - Candidate: `e0f8c5c` ("require auth for per-user data") and `aec8875`.
- **Implementation status:** Fixed (R3). Every personal-data route returns 401 without a session; `'default_user'` defaults are removed from `DbRepositoryService`; the in-memory PAN and application stores are filtered by `userId`; erasure also clears the caller's in-memory PANs and applications; the client demo login now obtains a real server session (development only).
- **Test result:** Regression tests in `tests/authHardening.test.ts` and `tests/securityRemediation.test.ts` pass after the fix and fail on `ebd30a0`.

### H1: Reflected XSS in the Upstox OAuth callback
- **Vulnerability:** XSS.
- **Severity:** High.
- **Affected file:** `src/app/api/auth/callback/upstox/route.ts`
- **Exact lines:**
  - `:8, 30` (the `error` query parameter)
  - `:200` (`err.message`, which includes the Upstox response body)
  - `:140` (`userName` and `userId` from Upstox)
- **Description:** URL parameters and upstream data are interpolated raw into an HTML response served from the app origin. The production CSP allows `'unsafe-inline'` scripts (M3), so injected scripts run.
- **Evidence:** `<pre>${error || 'Missing authorization code in callback parameters.'}</pre>`
- **Impact:**
  - A link to `/api/auth/callback/upstox?error=<script>…</script>` runs script on the IPOLENS origin.
  - Cookies are HttpOnly, but the script can still `fetch('/api/pans')`, `/api/auth/me`, `/api/portfolio/holdings` and others with the victim's cookies and send the data out, or act as the victim.
  - The alias `/api/auth/upstox/callback` forwards every parameter to this route.
- **Recommended fix:**
  - HTML-escape every interpolation (`escapeHtml` already exists in `sanitize.ts`), or return JSON or a redirect instead.
  - Never echo `err.message`.
  - Make the route admin and dev only (see M7).
  - Candidate: `2f02263` ("close Upstox OAuth XSS and CSRF").
- **Implementation status:** Fixed (R4). Every value written into the callback HTML is escaped with `escapeHtml`, including `error`, Upstox `user_name`/`user_id` and the exception text, which is generic in production. Ported from `2f02263`.
- **Test result:** Regression test in `tests/securityRemediationHigh.test.ts` (R4 suite) passes; it fails on `ebd30a0`.

### H2: Anyone can modify any IPO application by id; DELETE has no auth
- **Vulnerability:** IDOR/BOLA, broken access control, mass assignment.
- **Severity:** High.
- **Affected files:**
  - `src/app/api/applications/route.ts`
  - `src/lib/services/db-repository.service.ts`
- **Exact lines:**
  - `applications/route.ts:133-162` (PATCH) and `:164-182` (DELETE)
  - `db-repository.service.ts:221-245`
- **Description:**
  - PATCH has no session check, and updates `status` and `allottedShares` `where id = :id` with no owner condition. `status` can be any string, and `allottedShares` any number, negative included.
  - The response re-reads `getApplications()` with the default `'default_user'`.
  - DELETE has no auth either, though today it only filters the in-memory array.
  - IDs are `app_${Date.now()}_${4 base-36 chars}` (L7), so they can be guessed within a time window.
- **Evidence:** `.update(schema.ipoApplicationsTable).set({ status, allottedShares: … }).where(eq(schema.ipoApplicationsTable.id, id));`
- **Impact:** an attacker can falsify any user's allotment outcomes and share counts, which feed portfolio and P&L views.
- **Recommended fix:**
  - Require a session.
  - Use `where(and(eq(id), eq(userId, user.id)))`.
  - Use a Zod enum for status and bounded integers.
  - Return 404 when the caller doesn't own the application.
  - Candidate: `e0f8c5c` and `01d04e3`.
- **Implementation status:** Fixed (R3). PATCH and DELETE require a session; PATCH checks ownership first (404 otherwise), and the DB update now filters on `id` and `user_id`. Status and number validation (M5) is still open and belongs to R11.
- **Test result:** Regression tests in `tests/securityRemediation.test.ts` (H2 suite) pass after the fix and fail on `ebd30a0`.

### H3: Anyone can overwrite the shared DRHP index, and a GET changes state
- **Vulnerability:** Broken access control, data integrity (CSRF via GET), AI content poisoning.
- **Severity:** High.
- **Affected files:**
  - `src/app/api/analysis/route.ts`
  - `src/services/geminiAnalyst.ts`
  - `src/app/api/market/drhp-rag/route.ts`
  - `src/lib/services/drhp-rag.service.ts`
- **Exact lines:**
  - `analysis/route.ts:78, 86, 93`
  - `geminiAnalyst.ts:846-848, 1263`
  - `drhp-rag/route.ts:52, 61`
  - `drhp-rag.service.ts:60, 197-199`
- **Description:** text supplied without login (`drhpText` in a GET query or POST body, `customText`, or an uploaded file) is indexed under a ticker in the single `documentStore` Map that every user shares.
- **Evidence:**
  - `drhpRagService.indexDocument(resolvedSymbol, customDrhpText, …)`
  - `if (customText && customText.length > 50) { this.indexDocument(sym, customText, …) }`
- **Impact:**
  - An attacker can replace any IPO's prospectus content seen by all users with invented "facts", which then feed verdicts and Q&A. That is misinformation in a financial product.
  - It can be triggered by an `<img src>` pointing at the GET.
- **Recommended fix:**
  - Require login.
  - Keep user-supplied text in a per-user slot.
  - Let only server-side official sources write the shared index.
  - Remove `drhpText` from GET.
  - Candidate: `4b02df9`.
- **Implementation status:** Fixed (R10). User-supplied DRHP text, whether pasted, uploaded or sent as JSON, goes into a per-user slot (`indexUserDocument`, capped and LRU-evicted) that only that user reads. GET no longer accepts `drhpText`. All DRHP and analysis routes require login. Ported from `4b02df9`.
- **Test result:** Regression tests in `tests/securityRemediationHigh.test.ts` (R10 / H3 suite) pass; it fails on `ebd30a0`.

### H4: PDF decompression bomb and unbounded parsing, no login needed
- **Vulnerability:** Malicious upload, DoS.
- **Severity:** High.
- **Affected file:** `src/app/api/analysis/route.ts`
- **Exact lines:** `:7-71` (`extractPdfText`), `:23, :26` (`inflateSync` / `inflateRawSync`), and `:121-137`.
- **Description:**
  - Up to 200 FlateDecode streams are inflated with no `maxOutputLength`, from a file of up to 25 MB, with no login.
  - The whole file is scanned as one binary string by several regexes.
  - The type check is extension or MIME only, with no `%PDF-` magic check.
- **Evidence:** `decompressed = zlib.inflateSync(streamBuffer).toString('utf-8');`
- **Impact:** a crafted PDF of a few MB can expand to gigabytes on the event loop, exhausting memory or crashing the server.
- **Recommended fix:**
  - Require login.
  - Set `maxOutputLength` per stream and a total decompressed cap.
  - Add a magic-byte check.
  - Move parsing to a worker thread with time and memory limits.
  - Candidate: `4b02df9` (`pdfText.ts`).
- **Implementation status:** Fixed (R10). `src/lib/services/pdfText.ts` caps inflation at 8 MB per stream and 64 MB in total over at most 400 streams, finds stream markers with `indexOf` instead of a regex, and the route checks `%PDF-` magic bytes and rejects binary non-PDF uploads (415). Login is required. Ported from `4b02df9`. A worker thread for parsing is still open (checklist #63).
- **Test result:** Regression tests in `tests/securityRemediationHigh.test.ts` (a real 200 MB deflate bomb; 300 k stream markers) pass; it fails on `ebd30a0`.

### H5: Catastrophic regex backtracking (ReDoS) on unauthenticated auth input
- **Vulnerability:** ReDoS, DoS.
- **Severity:** High.
- **Affected files:**
  - `src/services/authStore.ts`
  - `src/lib/security/sanitize.ts`
- **Exact lines:**
  - `authStore.ts:90` (sign-up) and `:161` (Google)
  - `sanitize.ts:8` (`DANGEROUS_ATTRS_REGEX`), applied by `sanitizeString` to sign-in and sign-up fields and PAN form fields
- **Description:** both patterns take quadratic time, and there's no length cap before they run. No body-size limit exists (M6).
- **Evidence (measured locally on Node, regex in isolation):**

  | Pattern | Input | 20 k chars | 40 k chars |
  |---|---|---|---|
  | email `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` | `'a@' + '.'×N + '@'` | 1,050 ms | 4,137 ms |
  | `DANGEROUS_ATTRS_REGEX` | `'x' + ' '×N + 'x'` | 661 ms | 2,693 ms |

  Doubling N roughly quadruples the time. A 1 MB field would block the event loop for minutes.
- **Impact:** a single unauthenticated `POST /api/auth/signup` stalls the whole Node process for everyone.
- **Recommended fix:**
  - Cap lengths first: email ≤ 254, names ≤ 100.
  - Validate email in linear time: split on `@` and check the parts.
  - Rewrite `DANGEROUS_ATTRS_REGEX` without the leading `\s*`, or drop regex sanitising in favour of output escaping.
  - Add body limits (M6).
  - Candidate: `01ad1bf`.
- **Implementation status:** Fixed (R8). `isValidEmail` caps at 254 characters and replaces the backtracking regex in sign-up, Google sign-in and the client forms. The sanitiser's tag pattern now uses `[^<>]*`, and the attribute pattern anchors on `\b`; both run in linear time. Port of `01ad1bf`, plus the sanitiser fix, which the baseline had missed.

- **Severity:** Medium.
- **Affected files:**
  - `src/app/api/auth/signin/route.ts`
  - `src/app/api/auth/signup/route.ts`
  - `src/app/api/auth/google/route.ts`
  - `src/lib/security/session.ts`
- **Exact lines:**
  - `signin/route.ts:27`
  - `signup/route.ts:29`
  - `google/route.ts:25`
  - `session.ts:141-145`
- **Description:**
  - The HttpOnly cookie is undermined by also returning `token` in the response JSON.
  - Two cookies carry the same token.
  - `Authorization: Bearer` is accepted for every route, so CSRF-style Origin checks are moot for token holders.
- **Evidence:** `NextResponse.json({ success: true, user: result.user, token, … })`
- **Impact:** any script that runs during sign-in, or any logging proxy, can capture a 30-day session token.
- **Recommended fix:**
  - Drop `token` from responses.
  - Use one cookie, with the `__Host-` prefix.
  - Accept Bearer only on machine routes.
- **Implementation status:** Fixed (R15). Sign-in, sign-up and Google sign-in no longer return the token in JSON and set only the HttpOnly `ipolens_session` cookie (the `ipolens_token` duplicate is gone). `extractTokenFromRequest` no longer accepts `Authorization: Bearer` as a session; machine access to the scraper uses `CRON_SECRET`. Deferred: the `__Host-` cookie prefix, which would sign every user out.
- **Test result:** Regression tests in `tests/securityRemediationMedium.test.ts` (R15 suite) pass; it fails on `ebd30a0`. Also checked in the browser: `document.cookie` cannot see the session.

### M10: Upstox automation scripts hold the broker PIN and TOTP seed and open an unauthenticated listener
- **Vulnerability:** Exposed keys / secret handling, OAuth (no `state`).
- **Severity:** Medium (developer machine).
- **Affected files:**
  - `scripts/getUpstoxToken.mjs`
  - `scripts/devWithUpstox.mjs`
- **Exact lines:**
  - `getUpstoxToken.mjs:67-69, 84-86` (`UPSTOX_MOBILE`, `UPSTOX_PIN`, `UPSTOX_TOTP_KEY` from `.env.local`)
  - `:228-245` (rewrites `.env.local`)
  - `:338-343` (Puppeteer with `--no-sandbox`)
  - `:594-635` (`http.createServer` with `server.listen(port)` and no host, so it binds every interface; accepts any path containing `callback` or `upstox` with a `code`; no `state`)
  - `:657-663` (`exec` of a shell string containing the auth URL)
- **Description:**
  - The full broker login factors (mobile, PIN, **TOTP seed**) sit in plain text next to the token.
  - Anyone on the LAN can hit the listener.
  - Automating broker sign-in may break Upstox's terms of use.
- **Evidence:** the lines quoted above.
- **Impact:** leaking `.env.local` (backups, sync, accidental commit) hands over the broker account itself, not just a one-day token.
- **Recommended fix:**
  - Keep the PIN and TOTP seed in the OS keychain or a secret manager, or drop headless login.
  - Bind to `127.0.0.1`, add and check `state`.
  - Use `execFile` or `open` with arguments.
  - Remove `--no-sandbox`.
  - Document the risk.
- **Implementation status:** Fixed (R16), partially. `scripts/getUpstoxToken.mjs` adds a random OAuth `state` to both flows; the local callback server rejects redirects without it and listens on `127.0.0.1` only; the browser is opened with `execFile` (no shell); the Chromium sandbox stays on unless `UPSTOX_PUPPETEER_NO_SANDBOX=true`; and a header warns how to store the PIN and TOTP seed. **Still open:** the PIN and TOTP seed are still read from `.env.local`; moving them to an OS keychain or secret manager is your call (see the header note).
- **Test result:** Regression test in `tests/securityRemediationMedium.test.ts` (R16 suite) passes; it fails on `ebd30a0`.

### L1: CORS trusts every `*.ipolens.in` origin with credentials

### L2: Scraper sync: cookie-presence pre-check, shell exec and non-constant-time secret compare
- **Vulnerability:** Security misconfiguration, command-injection hygiene.
- **Severity:** Low.
- **Affected files:**
  - `src/proxy.ts`
  - `src/app/api/scraper/sync/route.ts`
- **Exact lines:**
  - `proxy.ts:76-95`
  - `route.ts:76, 79, 105-109`
- **Description:**
  - The proxy only checks that **some** session cookie exists. That's harmless, because the route itself requires `role === 'admin'` or `CRON_SECRET`.
  - The secret is compared with `===`.
  - `exec` runs an interpolated shell string. It's safe today, because `monthsBack` is clamped to an integer and the path is fixed.
  - Admin is reachable through C1.
- **Evidence:** ``const cmd = `python "${scriptPath}" --months ${monthsBack}`;``
- **Impact:** low now. It becomes command injection if any user value is added later.
- **Recommended fix:**
  - `execFile('python', [scriptPath, '--months', String(n)])`.
  - `crypto.timingSafeEqual` for the secret.
  - Make the proxy check validate the session, or remove it.
  - Candidate: `80abe41`.
- **Implementation status:** Fixed (R17). `execFile('python', [script, '--months', n])` with no shell; `CRON_SECRET` compared in constant time (SHA-256 then `timingSafeEqual`); the proxy's cookie-presence pre-check for the scraper is removed, because the route enforces admin or cron itself.
- **Test result:** Regression test in `tests/securityRemediationMedium.test.ts` (L2) passes; it fails on `ebd30a0`.

### L4: Long sessions, no idle timeout, per-process session cache
- **Vulnerability:** Session management.
- **Severity:** Low.
- **Affected files:**
  - `src/lib/security/session.ts`
  - the sign-up and Google routes
- **Exact lines:**
  - `session.ts:24, 31, 69-77`
  - `signup/route.ts:24`
  - `google/route.ts:19`
- **Description:**
  - Sign-up and Google sign-in always issue 30-day sessions, and `createSession` defaults to `rememberMe = true`.
  - There's no idle timeout.
  - A cached in-memory session stays valid on other instances after sign-out, until the process restarts.
  - Without a DB, sessions are memory-only.
- **Impact:** longer windows for stolen tokens, and inconsistent revocation.
- **Recommended fix:**
  - 1-day default with 30-day opt-in, and a 24-hour idle timeout.
  - The DB as the source of truth, with a short cache TTL.
  - Candidate: `80abe41` (idle timeout still open there).
- **Implementation status:** Fixed (R17), partially. Sessions default to 1 day; 30 days only through sign-in "remember me"; sign-up and Google sign-in use 1 day. In database mode, cached sessions are re-checked every 60 s, so a sign-out elsewhere takes effect across instances. **Still open:** an idle timeout, which needs a `last_seen` column (schema change deferred to the Supabase branch).
- **Test result:** Regression test in `tests/securityRemediationMedium.test.ts` (L4) passes; it fails on `ebd30a0`.
